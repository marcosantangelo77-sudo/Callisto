## What does not

### R1 — HIGH: the resume anti-laundering guard never verifies the HMAC (checkpoint.py)

`seal_guard`/`replay_ledger` verify sha256(body) == content_sha256 — but both
fields sit inside the *unsigned-by-check* payload. Every Checkpoint carries an
HMAC (`sig`) over the canonical record precisely so tampering is detectable,
and `load_by_key` faithfully loads it — yet **no code in the resume path ever
calls verify_signature** (grep confirms: only trusted_age_seconds checks it).
Reproduction (tests/test_review_2026-08-23.py::test_seal_guard_refuses_checkpoint_whose_signature_fails):
rewrite a checkpoint's fetch body AND recompute content_sha256 on disk, leave
the now-invalid sig in place, resume → seal_guard returns SEAL. C1/C2's
"integrity" reduces to attacker-writable fields. Owner: instance 1 (loop).
Fix direction: load_by_key (or replay_ledger) must treat an unverifiable
signature exactly as it treats a digest mismatch.

### R2 — MEDIUM: K1 fix half-landed — mean_brier/_verdict still trust unverifiable briers

ee549f8 correctly excluded truth-less rows from the calibration *bins*, but
`mean_brier` still averages r.brier over all scored rows regardless of whether
ANY row carries answer_binary, and `_verdict` grades on that mean. Reproduction
(test_verdict_does_not_praise_batches_with_zero_real_ground_truth): ten rows,
fabricated brier=0.001, answer_binary=None on every row → verdict is still
"strongly better than chance (Brier < 0.20)". That is the exact forgery K1's
commit message documents, surviving one level up in the same report object.
Owner: instance 1. Fix direction: mean_brier over rows with known truth only;
verdict must demand n_truth > 0 before any praise.
