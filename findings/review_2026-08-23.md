## WHAT DOES NOT

### R1 — CRITICAL (latent): StasisStop's guarantee is false outside its corpus

`stasis_stop.py` claims a round that changed neither independent keys
nor admitted shas proves "further rounds cannot alter tier/stance/
confidence". That inference requires the next round's CANDIDATE SET to
equal this one's. The retriever violates that premise one screen away:
on any round admitting nothing, `excluded.update(specs)` rotates the
candidate pool (retrieval.py:657–661), so later rounds query sources
NEVER YET TRIED. A leaf whose first two rounds were barren gets stopped
by stasis at round 2 while round 3 would have fetched from fresh,
relevant sources.

The 27-case proof cannot see this by construction: its own
distribution table shows round 1 was conclusion-moving in **27/27**
cases — no corpus case ever enters the exclusion-rotation path the bug
lives in. The proof is honest inside its world and inapplicable outside
it. Production does not wire the rule yet (disclosed by the author),
so this is currently latent — but the module was merged under a
guarantee ("provably cannot move") that is untrue, and the advertised
enablement path ("one line") would arm it.

Repro: `test_r1_stasis_must_not_stop_while_untried_sources_remain` —
six sources, fan-out 2, four barren then two relevant; baseline reaches
round 3 and seals sufficient, stasis run stops at round 2 with an empty
admitted set. Conclusion states differ; the test fails on master.

Minor adjacent defects in the same module: docstring says the rule "can
fire as early as after round 1" while the code requires two consecutive
states (fires earliest at round 2 — the inline comment admits this);
`observe_with_stasis` and `_State` are dead code (zero callers).

## NEW FAMILY (add to PATTERNS.md)

**9. A stop rule that proves the past and applies it to a changing
future (two instances).**

Shape: a termination layer fingerprints accumulated STATE and concludes
"no further step can change the outcome." Valid ONLY while the set of
future steps is determined by that state. Both retrieval stop rules
break this: the candidate pool mutates every round (barren rounds
exclude tried sources; planner marks unplannable; gain-skips remove
sources), so "nothing changed this round" never implies "nothing can
change next round."

- Instance 1: `StasisStop` (this pass, repro'd — R1).
- Instance 2: `InformationGainTerminator` as wired into the retriever
  (retrieval.py:463–467): its "confidence" is the indep-keys ratio, so
  two stagnant rounds stop the loop even while untried sources remain —
  same closed-world assumption, pre-existing, caught by the same repro
  harness with `max_rounds >= 4`.

Hunt instruction: for every stop/skip rule, ask "what sets the NEXT
step's inputs, and can anything change it that the fingerprint doesn't
cover?" A state fingerprint is a proof about the PAST; it becomes a
lie the moment the loop schedules different work.
