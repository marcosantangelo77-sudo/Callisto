## What does not — ranked

### R0 — f702bd6's merge narrative is false; parallel leaves are NOT on master

**Severity: highest. This is claim-vs-code failure in the audit trail itself.**

The master-HEAD commit message says: *"merge fix/ckpt-resume-gate onto
parallelised master — three-way, both behaviours kept ... the sequential
per-leaf for-loop stays replaced by the bounded gather + question-ordered
merge phase."* Every part of that is contradicted by the repository:

```
$ git rev-list --parents -n 1 f702bd6
f702bd6 102f319                      # ONE parent — not a merge at all
$ git grep -c "gather(" f702bd6 -- tools/pipeline/engine.py
(no match)                           # no gather anywhere in master's engine
$ git merge-base --is-ancestor cb31f64 master   # build/parallel-leaves tip
(NO)
$ git diff --stat master...build/dd-decomposition-diversity | tail -1
97 files changed, 12738 insertions(+), 230 deletions(-)   # 85 unmerged commits
```

The bounded-concurrency leaf execution exists only on `build/parallel-leaves`
and `build/dd-decomposition-diversity` — neither is an ancestor of master.
Master still runs leaves strictly sequentially. Consequences:

- Anyone auditing master's log believes leaf concurrency is live. It is not.
- The next merge of dd-decomposition-diversity will replay the *exact*
  silent-drop scenario this commit claims to have solved — the ckpt fix had
  to be re-landed by hand once already; it will need it again, because the
  fix landed here as a plain commit rather than a true merge.
- A false "three-way merge" description poisons the one thing this project's
  process relies on: trustworthy commit history.

Reproduction is the git evidence above; no unit test can assert git topology,
so R0 lives here rather than in pytest.

### R1 — `_trace_from_payload` does not restore `admitted` (docstring overclaims)

engine.py:634-641 claims to restore "admitted fetches, rejected items ...
independence keys". It restores everything except **admitted**
(and rounds/skipped_sources — see R2). `trace.admitted` stays `[]` on every
resumed run. Consumer today: `gaps.classify_gap` reads `trace.admitted` for
`n_admitted`; scoring happens to use `independent_keys` only, so confidence
numbers are unaffected — which is precisely how this kind of gap survives:
the number looks right, the audit record is wrong.

Repro: `test_resumed_trace_restores_admitted_fetches` (xfail strict) fails
with `len(tr.admitted) == 0` against one stored fetch;
`test_gap_classifier_sees_admissions_on_restored_trace` shows the consumer
view (`n_admitted=0`).

### R2 — fetch_leaf payload omits `trace.rounds`: resumed null-classification loses error disclosure

`_fetch_payload` stores fetches/rejections/keys/queries/stop_reason — never
`rounds`. On resume, `attempted_anything` is False and source errors vanish.
For an empty leaf whose sources ERRORED (no rejections), the resumed run's
`classify_null` verdict claims **"no fetch was attempted"** for fetches that
were attempted and failed; mixed cases lose the "coverage may be partial"
disclosure. Same status label usually survives, so nothing crashes — the
honesty layer just quietly degrades, contradicting the fix's headline claim.

Repro: `test_resumed_empty_leaf_does_not_claim_no_fetch_attempted`
(xfail strict): restored trace classifies as retrieval failure with "no
fetch was attempted"; the live-equivalent control discloses "HTTP 503".

### R3 — a THIRD copy of the membership rule, still unnormalised, plus dead second loop

102f319's title is "one membership rule, not two." There are three:

1. `retrieval.in_family` / `independence_key` loop 1 — normalised (fixed).
2. `why.py` — now delegating (fixed by 102f319).
3. `tools/sources/base.py:339 independence_family()` — raw
   `"spec_name in members"`, zero callers, docstring actively inviting
   future wiring ("the family key a source counts as toward
   min_independent_sources"). The day someone wires it,
   `'semantic_scholar'` vs `'semanticscholar'` drift re-inflates
   independence — the exact defect this repo fixed twice.

Also: `independence_key`'s second loop (retrieval.py:185-187) is dead code —
any raw hit is necessarily also a normalised hit — and is a standing
invitation to re-copy the unnormalised pattern.

Repro: `test_independence_family_membership_is_normalised` (xfail strict)
fails with `'semantic_scholar' == 'scholarly-aggregator'` → got
`'semantic_scholar'`.
