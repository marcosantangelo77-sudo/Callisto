## WHAT DOES NOT HOLD UP

### R1 — Checkpoint durability regressed: a mid-phase crash forfeits completed work

The serial engine saved each leaf's fetch AND answer checkpoint *immediately*
via `ckpt.run_stage` inside the per-leaf loop — "resume from the last good
step" is the advertised W3 contract. The parallel restructure moved both saves
behind phase-wide success:

- **Phase A** (retrieval): any leaf's exception raises at engine.py:580
  *before* the first `cp.save` at :613. Zero fetch checkpoints survive.
- **Phase B** (answers): exceptions raise at engine.py:659; the answer
  `cp.save`s at :697 live in the ordered-assembly loop, which never runs.
  Leaves whose model calls already succeeded are silently dropped.

Consequence: a crash during a 30-leaf crawl costs every paid model call, not
just the failing one. This contradicts MORNING_REPORT's checkpointing claim
("resume from the last good step") and the point of W3.

**Reproduction (differential, committed):**
`tests/test_review_checkpoint_partial_progress.py`

```
parallel branch:  FAILED — 0 answer checkpoints survive (assert >= 1)
master (serial):  PASSED — pins real serial behaviour, not my invention
```

The failure injection matches leaf text in the prompt rather than `_call_tag`
specifically because the serial engine never passes `_call_tag`; that choice is
what makes the test a differential repro rather than a parallel-only tautology.
Fix direction: save each answer's checkpoint inside `_answer_fresh` on
completion (payloads are self-contained; assembly order is independent of save
order), and replay-then-save per leaf before raising in Phase A.

### R2 — No test exercises MIXED resume (some stages hit, some fresh)

`test_checkpoint_resume_roundtrip_identical` resumes a fully-completed run —
every stage hits. But the new load/save split (`cp.load` up front at :567,
`cp.save` in assembly) exists precisely for partial state, i.e. run 1 crashed
mid-phase, run 2 has hits for early leaves and misses for the rest. That path
is where interleaved replay ordering and the split actually execute together,
and nothing covers it. The serial engine got partial-resume correctness free
from `run_stage`'s atomicity; the restructure had to re-earn it and didn't.

### R3 — Small test defects worth cleaning while the file is open

- `test_checkpoint_resume_roundtrip_identical` lines ~330-334: `f1`/`f2` are
  assigned and never used; the fingerprint is computed twice more with
  throwaway ledgers just to strip two keys. Dead weight in the most important
  test.
- The fingerprint records evidence *contents* but not per-item assigned
  source_class/confidence (leaf-level classes are pinned; item-level drift
  within a leaf would need to move a leaf aggregate to be caught).
- Wall-clock assertion `t5 < t1 * 3.0` is generous enough to pass a mildly
  degraded engine; acceptable as smoke, not as proof of overlap depth.

## LATENT HAZARDS (not defects today; one config change from being one)

- `SourceRegistry._tf_cache` (tools/sources/registry.py:113) is lazily built
  on first select and Phase A now calls it from N threads concurrently.
  Benign under CPython's GIL because the rebuilt content is identical, but it
  is unsynchronized shared mutable state on a hot path — one line of comment
  or a lock keeps the next person honest.
- Evidence reconstruction in ordered assembly rebuilds `Evidence` from six
  fields and drops `timestamp` (regenerated). Volatile either way, harmless
  today; noted so nobody assumes session dicts are field-complete.
- On a failed run the parallel engine's shared ledger holds NO records
  (raise precedes replay) whereas the serial engine's held earlier leaves'.
  Unobservable through PipelineResult, but code that retries on the same
  pipeline instance sees different ledger state than it would have under
  serial semantics.
