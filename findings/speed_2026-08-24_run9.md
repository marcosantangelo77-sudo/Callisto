### What run 8's numbers got wrong (self-correction)

Run 8 claimed "when Retry-After >= cap the fix correctly fails over". The live
A/B falsifies that framing: **the fresh-fork CLI that receives the very same
call survives Portal's capacity window** because its own session waits out the
~30s inside `hermes -z` and returns a good answer ~29–31s later. So failing
over does NOT escape the wait — it pays ~10–14s of process startup ON TOP of
the same window, and discards the warm fast endpoint to do it. Run 8's
"correctly fails over" was inferred, not measured; this run measured it.
