### RV-A (HIGH) — A2 never merged: gc() still destroys ALL cited evidence when the index corrupts, on master AND on this branch (family #2 across branches)

`tools/artifacts.py::gc()` reads the index as ground truth about
reachability. On master, `_load_index()` deliberately tolerates corruption
("objects survive") by returning `{}` — and gc() then deletes every object
not in `{}`, i.e. the entire store. One bit-rot event + one maintenance gc
call wipes every artifact a sealed conclusion cites.

The fix exists: commit d8f0b17 refuses to delete on a corrupt index (keep
garbage, never destroy evidence — correct failure direction per PATTERNS

### RV-B (MEDIUM) — edgar.py parses Retry-After with bare float(): a legal HTTP-date crashes out of the retry loop (family #2)

Four Retry-After handlers exist in this repo and they disagree:
- `inference.py::_retry_after_seconds` (new, run 8): guarded, capped. Good.
- `tools/sources/base.py:222`: try/except around float(), capped at
  MAX_RETRY_AFTER_S. Good.
- `tools/odds_api_io.py::_compute_backoff`: try/except, falls through to
  exponential backoff. Good.
- `tools/domains/finance/edgar.py:153`: `float(exc.headers.get(...) or 0)`
  with NO guard. RFC 7231 permits Retry-After as an HTTP-date; one 429 with
  a date header raises ValueError from inside the HTTPError handler — past
  the rate-limit branch, past the 5xx branch, out of `_get` entirely. The
  documented contract ("minimum inter-request gap plus Retry-After handling
  on 403/429") is false for a legal server response. Reproduced:
  `float('Wed, 21 Oct 2026 07:28:00 GMT') -> ValueError`.

Pinned failing in `test_edgar_retry_after_http_date_raises_valueerror_out_of_retry_loop`.
Fix direction: reuse the base.py pattern (guard + cap), or better, extract
one shared helper — four copies of the same rule is how this family exists.

### RV-C (MEDIUM) — sidak scope change (bc08880): the default scope does NOTHING, the sport fallback widens instead of narrows, and the test suite proves neither

Reviewed as work product, since no prior run examined it:

1. **"window" (the new DEFAULT) is byte-for-byte the lifetime denominator.**
   `scope_counts["window"] = max(lifetime_n, active_n, 1)` — identical to
   `"lifetime"`; only the log tag changes. The findings file argues for the
   decision cohort; the code implements it ONLY under `sport`. So the
   advertised behaviour change ("breaks the doom-loop causal chain") is off
   by default, and flipping the env var to the default value is a no-op.
   The inline comment admits it ("same query; semantics differ by declared
   claim") — a label standing in for evidence, family #4.
2. **Sport-scope fallback goes to the WIDEST denominator.** When the sport
   count is 0 (new sport, empty window — precisely when the engine is least
   calibrated), `scope_counts["sport"] = max(lifetime_n, active_n, 1)`,
   i.e. the lifetime pool. The tag honestly records "sport→window fallback",
   but window==lifetime, so the fallback lands on the harshest possible n.
   A fallback should degrade to the next-NARROWER set, not jump to the
   widest.
3. **The tests cannot catch either problem.** `test_sport_scope_denominator_
   query` executes a hand-copied SQL string against a fixture DB — it never
   calls `check_promotion_readiness`, so the production query could drift
   arbitrarily without a failure (family #7). `test_no_floor_at_any_scope`
   recomputes the Šidák formula from scratch and asserts arithmetic against
   itself; production code is absent from the assertion entirely.

The direction of the change is right (lifetime-pool ratchet was diagnosed
correctly), and it respects hard rule #2 (nothing automated may weaken a
gate — env-config only, argued first). But as landed: default-off no-op +
widening fallback + self-referential tests. It should be finished (window
actually filtering by lookback, narrow fallback, tests that call the real
method) or the misleading "window" label dropped until it is.
