## THE FINDING — the critic is banned from the fast tier

`agp/adversary.py:479` calls `complete(task_class, messages,
schema=VERDICT_JSON_SCHEMA)` — the adversary is the pipeline's ONLY
schema-bearing routed call. `ProviderRouter.candidates_for()` excludes any
endpoint with `structured_output: false` from schema-bearing calls UNLESS
its backend is `hermes_cli`. Measured on this machine:

    candidates_for("adversarial_review")             -> ['gpu1', 'ox_alpha_proxy', 'ox_alpha']
    candidates_for("adversarial_review", schema=...) -> ['gpu1', 'ox_alpha']

`ox_alpha_proxy` is openai_compat with an HONEST `structured_output: false`
declaration (upstream is JSON-in-text), so the critic can never ride the
proxy that serves the author. It always falls through to `ox_alpha` — the
fresh-fork CLI path (~12–14s process startup BEFORE its own Portal queue),
the exact cost the proxy exists to avoid — on one of the three serial
rounds of every sealed question.

The hermes_cli exemption exists precisely because best-effort JSON-in-text
plus the shared tolerant parser keeps a laptop running the whole system
(inference.py:1306–1313). The proxy serves THE SAME MODEL behind the SAME
Portal OAuth (parity established run 7, re-verified runs 9/11); excluding it
while exempting the CLI is an accident of backend naming, not a policy.
Battery D3's parse-retry/fail-closed machinery applies identically over
either transport.

Also verified live tonight: Portal ACCEPTS `response_format: json_schema`
through the proxy without erroring (200, valid JSON back) — so admission is
safe — while `_payload()` currently attaches response_format even to
endpoints declared unable to enforce it, which is dishonest about what the
request can achieve and would hard-400 on stricter OpenAI-compat providers.
