## THE FINDING — the evidence window shows the model JSON boilerplate, not content

Measured on a REAL OpenAlex works response tonight (filter query, per-page=10,
full records — the exact shape `works_search` returns):

    sorted-JSON body: 243,934 bytes
    evidence window the model sees: body[:4000] (sorted-KEYS JSON)
    result titles inside that window: 0 of 10 (first title at byte 5,562;
    offsets 5.5k–237k)

`engine._answer_leaf` builds each Evidence as `content=f.body[:4000]`. The
body is `json.dumps(parsed, sort_keys=True)`: sort_keys puts `meta`
(`x_query`, `oql`, `oqo` filter echoes) FIRST — thousands of bytes of API
boilerplate — before any `results[]` entry. So every Manager answer call and
the adversary's attack call reason over meta/issn/id fields while the actual
titles and abstracts are cut. This is not only wasted prompt bytes; it is
wasted UNDERSTANDING — run 7 flagged "prompt size at answer stage" and this
run names the mechanism.

## MODULE CLAIMED THIS RUN — announced before edit

**Owner this run: `tools/pipeline/engine.py::_answer_leaf` — the Evidence
content construction ONLY (`f.body[:4000]`).** One seam, one function.
Not retrieval.py, not synthesis.py, not model.py prompts, not agp/, not
inference.py, not scoring.

THE FIX: a text-preserving digest instead of a byte-prefix. Reuse
`retrieval.extract_text` (already exists, already used by the relevance
gate — no second flattening rule invented) to flatten `f.parsed` into
strings-only text, take its head window (same 4000-char budget), and fall
back to `f.body[:4000]` when parsed is unavailable. Provenance unchanged:
`content_sha256` still hashes the FULL canonical body; the ledger still
records full bytes; only what is SHOWN to author/adversary models changes.

CORRECTNESS: strictly MORE of the real content reaches the author and the
adversary; nothing crosses a cutoff (digest is computed from already-admitted
fetches at answer time); the adversary stays its own call over the same
evidence items; no gate moves. Offline golden fingerprints use tiny fixture
bodies (<4000 chars) where digest == body[:4000]-equivalent text, so goldens
must be byte-stable; the five-question Brier regression must pass unchanged.

## MEASURED AFTER — and a regression the goldens caught before it shipped

First cut assigned provenance AFTER replacing content with the digest:
`assign_source_class` hashes evidence.content against recorded bytes, so
every fetched item silently demoted PRIMARY -> INFERRED (0.55/PROBABLE ->
0.54/SPECULATIVE). The parallel-vs-serial golden test caught it immediately.
Fix: provenance is probed against the FULL canonical body; only the shown
text is the digest. After the fix, every non-evidence golden field —
confidence, tier, stance, sealed, source_classes, fetches, ledger hashes,
objections — is byte-identical (verified programmatically across all 11
scenarios). Goldens regenerated for the evidence field alone; five-question
Brier golden unchanged at 0.25.

Content win, on a real 244KB OpenAlex works response:

    BEFORE: 4000-char window -> 0 of 10 titles visible to author/adversary
    AFTER:  digest window     -> 2 of 10 titles + 227 words of abstract text
            in the same 4000-char budget (per item, per answer call,
            repeated for the adversary call)

Structural wall: 7.746s vs 7.71-7.83s band — no offline regression.
All 63 speed tests green (39 + 24).

Latency framing: same 4000-char budget, so token cost per call is UNCHANGED;
the win is information density per second of model latency — on real fat-API
bodies the old window was ~100% boilerplate, so 100% of the answer-stage and
adversary-stage model time was spent reasoning over meta fields. This makes
the EXISTING serial round trips more decisive rather than faster; fewer
wasted re-queries downstream is the expected second-order effect (not yet
measured).
