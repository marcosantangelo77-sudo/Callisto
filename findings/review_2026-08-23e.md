### R1 (HIGH) — the checkpoint HMAC is decorative on the replay/seal path EVEN WHEN a key is configured

Run 4 reproduced w3's D1 only in the unkeyed regime, leaving open "just set
CALLISTO_CUTOFF_KEY". I tested the keyed regime directly: save() signs,
then I rewrote body AND content_sha256 in the saved JSON (the attacker
controls both), loaded, replayed. Result: zero integrity failures, the
fabricated bytes enter the ledger as primary=True, `provenance_is_intact`
returns True, seal_guard would SEAL. Tampering produced_at alone also
passes the guard — the sig is consulted nowhere on this path; its ONLY
consumer is `trusted_age_seconds`, i.e. gc. Configuring a key changes
nothing for sealing. This is strictly worse than the stranded finding
suggests: the mitigation everyone assumed ("deploy with keys") closes only
the age-forgery hole.

Repro: `test_tampered_checkpoint_fails_provenance_guard_even_keyed` (both
parametrisations fail on master). Fix belongs to whoever owns
checkpoint.py: replay_ledger should refuse records whose `sig` fails
verification whenever a harness key exists.
