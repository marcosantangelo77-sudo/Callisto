## What does not — ranked

### RV1 (HIGH) — the sealed leaf confidence can be RAISED by round() (family 6, alive on master)

`engine.py:445` computes the stored/sealed leaf number as
`round(max(0.0, min(ec.estimate, ec.ceiling)), 2)` — round-half-up, not
`floor_conf`. The estimate-wiring commit preserved this deliberately
("historical rounding … preserved verbatim"), and its equivalence test pins
the bug along with the behaviour. `round(0.836, 2) == 0.84`: an automated
actor raising a confidence score, the exact defect the red team found 1,385
instances of elsewhere. Reproduced end to end:
`test_leaf_confidence_is_never_raised_by_rounding` — model proposes 0.836,
leaf stores 0.84. Fix: use `floor_conf`; the wiring test's equivalence pin
must then assert `sealable() == floor_conf(min(...))`, not `== round(...)`.

### RV2 (HIGH) — "PRIMARY" provenance is minted from any HTTP 200, so one topical fetch stores the model's self-reported confidence VERIFIED

`RestSource._record` records every successful body `primary=True`
unconditionally; `ProvenanceLedger.assign_source_class` maps primary bytes →
SourceClass.PRIMARY, whose ceiling is 1.0. Nothing downstream distinguishes
"a primary document" from "a server responded". Consequence, reproduced end
to end: one word-overlap-relevant fetch satisfies `min_source_tier=1`
(required class PRIMARY — granted by the same unconditional flag), the
evidence-requirement gate passes, and the leaf stores the model's
`proposed_confidence=0.95` as **VERIFIED 0.95**, with no downward mechanism
between proposal and storage. Only the inheritance rule's zero-descendant cap
(0.55) saved the parent seal in my probes — i.e., today the whole
anti-self-report architecture hangs on descendants being unresolved.
Repros: `test_single_fetch_cannot_store_model_confidence_verbatim`,
`test_primary_assignment_requires_more_than_a_200`. Fix direction: PRIMARY
assignment should require evidence of document character (content-type/
schema match per adapter), or fetch records should carry an adapter-declared
class; the status-code-derived flag alone cannot back VERIFIED.

### RV3 (MEDIUM) — replay_ledger() itself still authenticates nothing under a key (family 1, one frame below D3's fix)

D3 routed both ENGINE call sites through `partition_admissibility`, but
`replay_ledger()` — the public function whose job is minting ledger entries —
still checks only `content_sha256`, both fields attacker-writable. Under a
keyed regime a checkpoint whose HMAC fails replays fine if anyone calls the
function directly (future callers will; that is why it is public).
`findings/fix_d3.md` claims "A signature that fails is never replayed into
the ledger at all" — true of the two current callers, false of the module
API. Repro: `test_replay_ledger_refuses_bad_signature_when_keyed`. Fix:
replay_ledger should consult the same predicate (or refuse unsigned records
when a harness key exists), restoring "one definition" at every frame.
