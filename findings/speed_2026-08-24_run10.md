## THE FINDING — run 9's patience is per-SLEEP, not per-CALL

Run 9 raised the single-sleep cap from 10s to `_429_PATIENCE_S = 35` and
measured it as a win. Tonight's live pattern breaks it: Portal serves
**consecutive** Retry-After:30 windows. With attempts=2:

1. first attempt → 429 Retry-After:30 (≤35, honoured) → sleep 30s
2. retry → ANOTHER 429 Retry-After:30 → **raise** → failover

Result: 30+s burned in-place, THEN a fresh-fork CLI call anyway — the exact
run-8 disease one sleep later. Raw-curl control showed windows stack for
60–128s under load. Run 9's own report hinted at this ("two consecutive 429
windows" caused legitimate-looking failovers on calls 3–4); this run named
the mechanism.

## MODULE CLAIMED THIS RUN: `inference.py` — `_post_with_retry` / `_retry_after_seconds`, patience accounting ONLY

Change: `waited` accumulates total seconds slept on 429s for ONE call; a
Retry-After is declined only when `waited + retry_after > _429_PATIENCE_S`.
The fixed cap inside `_retry_after_seconds` is gone (a single honest 30s
header is no longer artificially declined). Bounded by construction: ≤35s of
sleeping per call, attempts still 2, exhaustion still propagates to the
unchanged failover chain, non-429 4xx unchanged. No caching, no cutoff
contact, adversary untouched, no gate moved — only WHEN the identical
completion waits vs forks.
