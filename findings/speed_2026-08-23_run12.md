## MODULE CLAIMED THIS RUN — announced before edit

**Owner this run: `inference.py::_post_with_retry` — connect-phase failure
policy ONLY.** Nothing else touched: not endpoint ordering, not cooldown math,
not candidates_for, not config/providers.yaml, not tools/pipeline/*, not agp/,
not any scoring path.

THE DEFECT: `_post_with_retry` retries EVERY `httpx.TransportError` in place —
sleep 0.5s, attempt again. For connect-phase failures (`httpx.ConnectError`,
`httpx.ConnectTimeout`) that is pure waste: no bytes were sent, so there is
nothing transient to recover from in 500ms. Tonight it taxes every fresh router
~0.5s per dead hop (measured 0.528s vs ~0.013s of actual refusal). On a host
that drops SYN instead of refusing, the same code DOUBLES a full connect-timeout
hang before failover — the run-8 "~10s dead failover" pattern, reproduced at
config-order scale.

THE FIX: connect-phase errors propagate IMMEDIATELY to the existing failover
chain (no in-place attempt consumed, no backoff sleep). Read/write-phase
transport errors and 5xx keep today's exact retry shape; 429 patience accounting
(run 10) is untouched; attempts semantics for non-connect errors unchanged.

CORRECTNESS ANALYSIS: which model serves is unchanged on every path where a
model actually serves — a refused socket served nothing before and serves
nothing after; failover order below the dead hop is untouched. When a GPU box
comes back mid-question it is still probed again after its cooldown expires
(record_failure still runs; ladder unchanged). No caching, nothing crosses a
retrodiction cutoff, the adversary stays its own separate model call, no gate or
threshold moves. Offline pipeline never enters the router → byte-identical.
